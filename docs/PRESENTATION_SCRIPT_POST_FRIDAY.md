## 1. คอม — เปิดงาน + สิ่งที่อาจารย์สั่ง + Role

### สคริปต์เปิด (~45 วินาที)

> “สวัสดีครับ ทีมมี 4 คนจะผลัดกันรายงานครับ  
> คอม ซี พาร์ท และเจ  
> วันนี้โฟกัสว่า **หลังคุยกับอาจารย์วันศุกร์** ทีมแก้และเพิ่มเติมอะไรไปบ้าง  
> ไม่รีวิวทั้งระบบใหม่ แต่เทียบกับข้อเสนอแนะรอบนั้นโดยตรงครับ”

### สิ่งที่อาจารย์เน้นวันศุกร์ (พูดชี้ตาราง ~1 นาที)

> “วันศุกร์อาจารย์เน้นหลายจุดหลัก ๆ  
> **หนึ่ง** แยกสิทธิ์ Admin / Internal / External ให้ชัด และอธิบาย Auth  
> **สอง** UI/UX สถานะจองให้สีชัด ปุ่มไม่ปนกับสถานะ  
> **สาม** Dashboard Admin กรองตามช่วงวัน ดูรายได้และอัตราใช้งานได้  
> **สี่** Log ต้องผูกกับการจอง ดูประวัติได้  
> **ห้า** มีแผน Testing และพิจารณา Payment เช่น Stripe  
> ตอนนี้ทีมปิดเกือบครบแล้ว เหลือ Stripe ที่ทำเป็นเอกสารศึกษาไว้ก่อน ตามลำดับที่อาจารย์แนะนำว่า core + test ก่อนครับ”

### Role / Auth ที่ปรับแล้ว (~1 นาที — โชว์ Admin Users ถ้าได้)

> “เรื่องสิทธิ์ เราปรับตามที่คุยไว้แล้วครับ  
> - อีเมล `@mfu.ac.th` เป็น **internal**  
> - `@lamduan.mfu.ac.th` และโดเมนอื่นเป็น **external**  
> - **Admin ไม่ได้ผูกโดเมนอัตโนมัติ** แต่ **promote ในระบบ** หรือใช้ `DEV_ADMIN_EMAILS` ตอนทดสอบ  
> ฝั่ง Security ยังยืนยันตัวตนด้วย Google OAuth แล้ว Backend ออก JWT เก็บใน HttpOnly cookie  
> หน้าเว็บมี route guard แต่สิทธิ์จริงอยู่ที่ API ครับ”

### ส่งไม้ต่อ

> “ต่อไปซีจะเล่าเรื่องสถานะการจองและ UX ฝั่งผู้ใช้ครับ”

## 2. ซี — UX สถานะจอง + โปรไฟล์ + หน้าผู้ใช้

### สคริปต์เปิด

> “สวัสดีค่ะ/ครับ ซีครับ/ค่ะ  
> ส่วนที่รับผิดชอบคือ UX การจองและหน้าผู้ใช้ ตามที่อาจารย์บอกว่าสถานะต้องอ่านง่าย และแยก ‘จ่ายแล้ว’ กับ ‘สำเร็จแล้ว’ ให้ชัด”

### สถานะจอง (ชี้จอ Dashboard ผู้ใช้ / Admin)

> “ตอนนี้สถานะหลักเป็นแบบนี้ครับ/ค่ะ  

| สถานะ | ความหมายสั้น ๆ |
|--------|----------------|
| รออนุมัติ | ส่งคำขอแล้ว รอเจ้าหน้าที่ |
| รอชำระเงิน | อนุมัติแล้ว รอจ่าย |
| ชำระเงินแล้ว | จ่ายครบแล้ว |
| สำเร็จแล้ว | เลยวัน/เวลาใช้งานแล้ว (ระบบอัปเดตอัตโนมัติ) |
| มีรีวิวแล้ว | badge แยก — ไม่ปนกับสถานะหลัก |
| ไม่อนุมัติ / ยกเลิกแล้ว | จบแบบไม่ใช้บริการ |

> สีและไอคอนใช้ชุดเดียวกันทั้ง User กับ Admin  
> ปุ่มอย่าง ‘อนุมัติ’ หรือ ‘จำลองชำระเงิน’ เป็น action แยก ไม่ใช้สีเดียวกับ badge สถานะครับ/ค่ะ”

### โปรไฟล์ / ฟอร์มจอง

> “โปรไฟล์แก้ชื่อได้ และ**บังคับเบอร์โทร** ทั้งตอนจองและในโปรไฟล์  
> ชื่อกับประเภทหน่วยงานดึงจากโปรไฟล์/Google ไม่ให้พิมพ์มั่ว  
> ผู้จองเห็นชื่อ admin ที่ดำเนินการ และเหตุผลถ้าไม่อนุมัติได้ชัดขึ้นครับ/ค่ะ”

### หน้าผู้ใช้อื่นที่ปรับสั้น ๆ (อย่ารายละเอียดยาว)

> “เพิ่มเติมที่ผู้ใช้สัมผัสได้ เช่น การแจ้งเตือนใน Navbar ดึงจากระบบจริงเมื่อมี Broadcast หรือเปลี่ยนสถานะจอง  
> หน้าแรกมี Banner จาก Admin จริง และพื้นที่แนะนำเรียงจากความถี่การจองจริงครับ/ค่ะ”

### ส่งไม้ต่อ

> “ต่อไปพาร์ทจะโชว์ฝั่ง Admin Dashboard และเครื่องมือเจ้าหน้าที่ครับ/ค่ะ”

## 3. พาร์ท — Admin Dashboard / Log / เครื่องมือเจ้าหน้าที่

### สคริปต์เปิด

> “สวัสดีครับ/ค่ะ พาร์ทครับ/ค่ะ  
> โฟกัสฝั่งเจ้าหน้าที่ ตามที่อาจารย์อยากให้ Dashboard กรองช่วงเวลาได้ และ Log ผูกกับการจอง”

### Dashboard (คลิกโชว์ตัวกรอง)

> “Admin Dashboard ตอนนี้กรองได้หลายโหมดครับ/ค่ะ  
> **เดือนล่าสุด / ทั้งหมด / เลือกเดือน / รายปี / ช่วงวัน**  
> ตัวเลขรออนุมัติ อนุมัติแล้ว ชำระเงินแล้ว และรายได้ จะตามช่วงที่เลือก  
> มีกราฟแนวโน้มรายได้ สัดส่วนประเภทผู้เช่า และอัตราการใช้งานห้อง Top 5 ตามช่วงที่กรองครับ/ค่ะ”

### จัดการคำขอจอง + Log

> “ในหน้าจัดการคำขอจอง  
> - อนุมัติ / ไม่อนุมัติได้  
> - ดาวน์โหลดเอกสารเป็น ZIP ได้เมื่อมีไฟล์แนบ  
> - มีปุ่ม **ดูประวัติ** ผูก `booking_id` เห็นว่าใครทำอะไรกับคำขอนั้น  
> แก้บัคที่เช็คบ็อกซ์ ZIP กดไม่ได้ เพราะไม่ได้ map URL เอกสารจาก API เรียบร้อยแล้วครับ/ค่ะ”

### ฟีเจอร์ Admin อื่นที่ปิดรอบนี้ (พูดสั้น เลือก 2–3 ข้อ)

> “รอบนี้ยังปิดงานเสริมที่ใช้งานจริงได้แล้ว เช่น  
> - **Broadcast** ส่งประกาศเข้า notifications จริง ไม่ใช่ mock  
> - **Banner** CRUD แล้วโชว์หน้าแรก  
> - นำเข้าห้องจาก Excel (แก้ path ที่ 404)  
> - จัดการผู้ใช้ promote admin / ตั้ง co-op  
> - รหัสส่วนลดลบได้ และคิดเป็นเปอร์เซ็นต์ถูกต้อง  
> Admin บังคับภาษาไทยอย่างเดียวตามการใช้งานเจ้าหน้าที่ครับ/ค่ะ”

### ส่งไม้ต่อ

> “ต่อไปเจจะสรุป Testing, การอัปเดตสถานะอัตโนมัติ และเรื่อง Payment ครับ/ค่ะ”

## 4. เจ — Testing + Cron + Payment + ปิดงาน

### สคริปต์เปิด

> “สวัสดีครับ/ค่ะ เจครับ/ค่ะ  
> ส่วนสุดท้ายคือการพิสูจน์ว่าระบบทำงานถูก และการวางแผน Payment ตามที่อาจารย์ถามวันศุกร์”

### Testing

> “เรามีแผนทดสอบแยกโมดูลใน `TESTING_PLAN.md` แล้วครับ/ค่ะ  
> ครอบคลุม Auth, Authorization, โฟลว์จอง, Admin และ Payment  
> ฝั่ง automated มี Vitest ฝั่ง backend, มี CI และมีการแก้เคสที่เคย fail ใน pipeline  
> ตามที่อาจารย์แนะนำ เราถือว่าฟังก์ชันหลักต้องมี test รองรับก่อน แล้วค่อยต่อ gateway จริงครับ/ค่ะ”

### Cron / สถานะอัตโนมัติ

> “สถานะ ‘สำเร็จแล้ว’ ไม่ต้องกดมือทุกครั้ง  
> มี job อัปเดตตามวันและช่วงเวลาใช้งาน เช้า / บ่าย / เต็มวัน  
> และยกเลิกคำขอที่ค้างเกินกำหนดได้ครับ/ค่ะ”

### Payment (พูดตรง ๆ — อย่าขายเกิน)

> “เรื่อง Payment Gateway เช่น Stripe  
> ทีม**ศึกษาและจดโน้ตเปรียบเทียบ**ไว้แล้ว ใน `PAYMENT_STRIPE_NOTES.md`  
> ระบบเรามีโครง adapter อยู่แล้ว — ตอนนี้ใช้ **mock_sandbox** สำหรับ UAT/Demo  
> และมี PromptPay QR อยู่แล้วสำหรับบริบทไทย  
> **ยังไม่ผูก Stripe จริง** เพราะอยากให้หน่วยงานเลือก provider และทำหลัง core + test แน่น ตามลำดับที่อาจารย์แนะนำครับ/ค่ะ”

### ปิดงานทั้งทีม (~30–45 วินาที)

> “สรุปสั้น ๆ หลังวันศุกร์  
> - Role / Auth ชัดขึ้น  
> - UX สถานะจองและโปรไฟล์ครบตามที่คุย  
> - Admin Dashboard + Log + เครื่องมือเจ้าหน้าที่ใช้งานได้จริงหลายจุด  
> - Testing และ cron พร้อมอธิบาย  
> - Stripe อยู่ขั้นศึกษา ยังไม่ integrate  
> วันนี้ขอรับฟีดแบ็กเพิ่มเติมว่าจุดไหนอยากให้ปรับต่อครับ/ค่ะ ขอบคุณครับ/ค่ะ”
